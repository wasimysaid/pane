# Run background work beside calls, owned by the package's generation

Proposed 2026-09-29 by the implementation of #47, extended by #48; not yet confirmed by the user. Q15 accepted scheduled work and explicit background services without activating installed packages by default ([ADR 0005](0005-lazy-activation-and-managed-dependencies.md)). Until #47 every guest call was asked for by the user (opening, an action, a search) and the runtime served them one at a time on its thread, each to completion or to its generation's end.

A [scheduled task](../background.md)'s run is **background work**: the runtime starts it in an instance of its own (`Request::Background`), never the command's call instance, and keeps its future in a list it polls whenever it looks for the next request and while it serves a call. A run waiting on a clock or a web request therefore holds back no call, of its package or another, and a call finishing never waits for it. Each run is owned by the generation current when it was asked for, exactly like a call ([generations](../generations.md)): when that generation ends, or the launcher drops the run's stop handle (the user turned the schedule off), the future and its instance are dropped where they wait and a late answer is discarded. A run's trap is reported to the health report like a call's, so crashes pause a package by the one existing rule; no separate rule for repeated background failures was added.

Why an instance of its own: a component instance serves one task's state, and Wasmtime offers no way to cancel one call of an instance and keep it ([ADR 0018](0018-extensions-reach-the-network-through-wasi-http.md)); stopping a run must not drop the instance the user's open command is using, and the command's calls must not wait on the run. The cost is an instantiation per run, and memory is not kept between runs (extension data is). Operations are not served in background work: they need the caller's frame and call chain, which only calls have; a run's operation call is refused.

A [continuing service](../background.md#continuing-services) (#48) is the same kind of work (`Work::Service`), started by the same driver: it runs until it returns, its generation ends or the user stops it, and a new generation starts it again at once. Its status comes back through one import, `pane:extension/service-status`, which the runtime links for every command but answers only in the instance running the service (a sink the launcher hands it, which drops a status from a run that is no longer current); the alternative of reading a status the service writes to its extension data was rejected because it would outlive the run and mix Pane's display with the extension's records. An error or a crash restarts it a fixed minute later on the launcher's clock: long enough not to spin, short enough for three crashes to fall within the five-minute pause window, so repeated crashes pause it by the existing rule without a rule of its own.

What decides when a run starts is the launcher, not the runtime: a thread of its own (`pane-background`, a current-thread Tokio runtime) starts what is due and waits for a clock (`pane_core::clock::Clock`), a change of the launcher's state or a run's end. The window's thread never waits for background work; the lasting status is written to Manage extensions' rows and records (`schedules.json`, `services.json`). The clock is injected (`Launcher::with_background`), so tests move a manual clock instead of waiting, and a launcher without it runs no background work at all.

The watchdog of [#18](https://github.com/hoangvu12/pane/issues/18) (CPU-time metering, progress-based) is meant to meet background work on these terms, which matter most for a service, whose run is meant never to end: a run is judged by the CPU time of each slice it computes before yielding, never by how long it has been running or waiting in total, since waiting is its normal state; a slice that computes too long without yielding is a hang of the package whether the slice is a call's or a run's. Background code must therefore await rather than compute for long, which the author instructions say. Until #18 lands, a run computing without yielding holds the runtime thread as a call would.

Costs: one more kind of runtime work to keep correct against every generation end; one runtime thread still serves everything, so background work only helps while it waits; a task's run lost to a runtime crash is not made again (like a call), while a service lost to one starts again a minute later; scheduling uses the wall clock, re-read at least every 30 seconds, so a clock change or sleep delays a run by up to that.
